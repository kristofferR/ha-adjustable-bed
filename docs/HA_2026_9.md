# Home Assistant 2026.9 baseline for v4

v4 requires Home Assistant **2026.9.0 or newer**. HACS enforces this minimum.
Development uses Python 3.14.2 or newer, matching HA's September requirement.
The CI `minimum-ha` job installs HA 2026.9.0 with its matching test helper
(0.13.363); the main test jobs resolve the current supported stack.
Both jobs install the Bluetooth and ESPHome requirements from that HA release's
own manifests using `scripts/ha_bluetooth_test_requirements.py`, then run with
`uv run --no-sync` so dependency resolution cannot replace those pins. The
integration does not override HA's Bluetooth dependency versions.

## Backup and rollback

**Create and download a Home Assistant backup before upgrading from v3.**
Include the Home Assistant configuration, custom integrations, registry data,
dashboards, and database if history needs to be restored. Keep the backup and
its encryption emergency kit outside the Home Assistant installation. See
[Home Assistant's backup and restore instructions](https://www.home-assistant.io/common-tasks/general/#backups)
and [backup emergency kit](https://www.home-assistant.io/more-info/backup-emergency-kit/).

v4 advances config entries to schema version 4, including standalone beds.
The v3 integration rejects entries newer than version 3. Unpairing a combined
bed changes its topology but does not downgrade its schema. Replacing the
integration files with v3 therefore does not provide a working rollback.

To return to the pre-upgrade installation:

1. Keep a separate backup of the current installation if you need to preserve
   changes made since upgrading.
2. Restore the **pre-v4** Home Assistant backup using the supported restore
   procedure for your installation. Restore its configuration and custom
   integration files together so the v3 code and stored state match.
3. After restart, verify the Adjustable Bed version, standalone entries, entity
   IDs, dashboard controls, and saved automation targets against that backup.
   A restore also rolls back other Home Assistant changes covered by the backup.

Do not manually change version fields in `.storage`: that does not reverse
registry ownership or paired configuration changes. If there is no pre-v4
backup, remain on v4 and report the problem before deleting devices or entries.

The automated migration checks and remaining installed-system validation are
listed in the [v4 validation matrix](V4_VALIDATION.md). A real backup restore
on the final release candidate remains a release gate, not a claim made by
the automated tests.

## Combined beds and native child devices

A combined bed has one parent device and a native child for each side, including
beds with a single Bluetooth address. Combined controls belong to the parent;
side controls belong to their child. The existing Left / Both / Right card uses
these relationships without changing its layout. Side ordering follows entity
side metadata before user-assigned device names.

Existing two-address side devices convert in place, retaining device IDs,
entity unique IDs, entity IDs, history links, and device customizations. Source
standalone entries are absorbed before their devices become children. Until
that succeeds, their devices remain owned by the original entries. An older
paired beta migrates during setup. A single-address pair retains its physical
parent ID and gains two logical children; its existing entity IDs are unchanged.

HA child records omit hardware fields. The paired config entry therefore stores
physical manufacturer, model, version, connection, and serial metadata in
`pair_physical_devices`, keyed by side. Diagnostics retain this evidence and
redact serial numbers, configuration URLs, names, PINs, and MAC suffixes.
Standalone beds retain their existing registry representation.

Unpairing two-address beds unloads the pair, restores each child's full device
record through HA's deleted-device restoration API, and transfers ownership to
the standalone entry. Entity rows are temporarily detached while the device
removal event is handled, then reattached to the same restored device ID. This
prevents HA's removal listener from deleting their registry identities. The
existing ownership journal handles subsequent transfer failures. Unpairing a
single-address bed keeps the physical parent and preserves original entity rows
before removing the now-unused logical children.

Targeting the parent defaults to both sides. Targeting a child defaults to its
side. An explicit conflicting `side`, including `both` on a child, is rejected
before commands run. Selecting both children coalesces into one both-side
operation. HA's new service validation helper excludes native child devices,
so the integration validates their parent and retains the child for routing.
Support-bundle resolution uses the registry helper that also permits unloaded
entries; a two-address parent still requires selecting a side.

## Bluetooth changes

- **Scan again for beds** explicitly requests HA's on-demand active scan behind
  the setup progress screen, then refreshes discovery. Re-entering the progress
  step reuses its task; closing the flow cancels it. Scan failure returns an
  actionable error without discarding manual setup. HA deduplicates concurrent
  requests and controls scanner eligibility and duration.
- Adapter selection uses HA's per-scanner device records and the existing
  connection-path ranking, retaining the selected scanner's BLEDevice and RSSI.
  Excluded adapters cannot re-enter through the generic fallback. A preferred
  adapter is a request: HA can reroute at connection time, and the coordinator
  records the actual source.
- Failed attempts and exported diagnostics include HA's connection-reachability
  explanation. This prose is advisory and never parsed to make routing decisions.
  Standard HA diagnostics redact MAC suffixes; support bundles preserve full
  addresses for matching beds, scanners, and connection attempts while redacting
  PIN fields. Failure to obtain it cannot replace the original error.
- Cancellation after link establishment releases integration-owned connections,
  startup subscriptions, and hydration work. Existing connection locks,
  intentional-disconnect handling, STOP cleanup, and paired failure handling
  remain in place.
- The stale-connection helper is imported and awaited directly from HA's managed
  dependency. Backend-specific capability checks remain; the obsolete optional
  import and awaitability compatibility branches are removed.

The integration currently reads advertisement snapshots and polls freshness;
it does not own a Bluetooth advertisement callback subscription. There is no
appropriate callback to switch to the new replay option. Adding a redundant
subscription would not improve discovery, so this audit deliberately leaves
replay unused.

HA 2026.9 supplies proxy disappearance, connection-slot, scanner removal, and
rediscovery fixes through habluetooth 6.26.11 and bleak-esphome 4.0.0. We retain
integration cleanup rather than duplicate the libraries' slot/scanner machinery.
Focused failure injection covers slot-wait failure, cancellation before and after
link establishment, scanner disappearance, subsequent reconnect, migration
rollback, service routing, and redaction. Existing tests cover stale connected
state, intentional disconnect, command/STOP serialization, and pair failures.
These are software checks; physical proxy and bed validation remains beta testing.

## Tracking and boundaries

This change implements #584 through #590 under #583. #585's callback replay item
is an audited no-op, as explained above. Cover speed support (#591) remains a
conditional follow-up because it needs protocol-specific capability evidence.
Topology extraction (#524), paired concurrent scheduling (#516), and hardware
protocol changes are outside this migration.
