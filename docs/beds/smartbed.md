# SmartBed by Okin

**Status:** Not yet tested (the SmartBed 2.4.2 profiles)

**Credit:** Reverse engineering by [kristofferR](https://github.com/kristofferR/ha-adjustable-bed)

## Known Models

- Amada and other OKIN receivers used with SmartBed.
- CB, Standard, Dacheng, CB24, CB27, CB24AB, CB1221 and CB27New receivers.
- Bluetooth names beginning `Headboard126` or `Headboard265`.

## Features

| Feature | Supported |
|---------|-----------|
| Motor control | Head, feet, head tilt, lumbar and hips, according to the selected layout |
| Headboards | Independent left and right headboard controls |
| Position feedback | No |
| Presets | Flat, zero gravity, anti-snore, lounge and TV, according to the receiver |
| Memories | M1; M2 on P3, P4 and P5 |
| Save | Confirmed saves; older receivers repeat recall for the app's long-save gesture |
| Massage | Direct intensity, wave and 10/20/30 minute timers |
| Light | Toggle on older receivers; discrete on/off on P5, including its RGB-flag route |
| Sonic module | Capability-gated intensity, wave, mode and timer |
| Clock and alarm | Shared Set bed clock and Set alarm actions on P2 through P5 |
| Single-address sides | CB24AB only |

### Framing and checksum

P1 uses the Okin ORE encoder. P2 uses the checked little-endian Keeson E6
encoder with an extra byte. P3 and P4 use the Okin N-frame encoder and parameter
records. P5 uses SoundWave's AA/2A record encoder, retaining each command's own
size field and marker. Profiles supply the command words and calendar transforms.

### Write mode

The app does not override the discovered characteristic's write type. Home
Assistant uses the exact matching service/characteristic and its live properties,
with acknowledged writes when supported and unacknowledged writes otherwise.
Actual receiver GATT properties and firmware behavior remain unverified.

### Responses

P1 preserves the signed-opcode arithmetic and either-header acceptance of the app.
CB status uses its persistent fragment prefix and length-specific intensity,
wave and timer fields. P3 profiles use their own massage and alarm handlers.
Dacheng receives side records with BCD alarm time, despite transmitting P2.
CB24 with five motors transmits P4 BCD time and receives raw CB24 alarm fields.
CB24AB keeps separate left, right and combined state. A combined alarm is enabled
only when both side records agree.

P5 configuration pages supply motor and massage counts, light type and the sonic
module. Remaining pages are queried highest first. Every page query clears the
sonic flag, as in the app. P5 massage, light, alarm and sonic handlers can fall
through to the manager's legacy parser, including its state overwrites.
Malformed short frames are rejected without partial updates. No checksum or
position-feedback interpretation is added to these notifications.

### STOP and release behavior

Movement refreshes at the selected profile's cadence until release or its bounded
HA hold ends. Cleanup sends STOP after the profile's release delay with a fresh
cancellation event. Disconnects invalidate every callback and pending write; an
old operation cannot send STOP to a replacement connection.

### Vectors

`tests/test_smartbed_vectors.py` compares all frozen builder and profile parser
cases. `tests/test_okin_cb24.py` covers live callers, cleanup, callbacks and setup.
The vectors are static Java/source-model examples, not physical BLE captures.

#### Setup

The app's ordered factory checks raw scan records before names: Standard,
Dacheng, CB24, CB27, CB24AB, CB1221, CB27New, then the two headboards and CB.
Home Assistant does not expose the complete raw scan record as manufacturer data.
It therefore uses the explicit receiver choice for ambiguous old devices and
keeps the established CB24 default. When raw records are available the selector
keeps the source's order and capability derivation, with safe length checks.
Headboards retain Flat, M1 and M2 without a light control. Headboard265 has two
wave choices and head/foot intensity, without a timer.
CB27New's exact name-length rule and the case-sensitive headboard prefixes are
available without raw data. No BLE PIN, authentication or explicit bond exchange
is required by these profiles.

#### Controls

Use the generated tables for each builder's actual frames. P2 cannot send hips
or M2 commands. Its absolute intensity is shared across massage zones. P4 uses
different hips masks and alarm choices. Older light and massage on/off controls
that send the same toggle frame remain toggles, rather than assumed inverse pairs.
Raw configuration bytes, parser state and capability metadata stay in diagnostics.

#### Timing

Old recall taps stay below the save threshold and send release cleanup. Explicit
save controls repeat the old recall gesture for the profile's save duration;
firmware interpretation remains unverified. P5 recalls and explicit saves each
send one distinct frame. Save buttons cannot be held in the dashboard card.

P5's head, foot and wave arrows read the live receive cache and send absolute
setters, followed by a status query after 200 ms. They do not update that cache
optimistically. Light changes query after 100 ms; sonic changes query after
200 ms. Old massage controls release with STOP and query after 500 ms. Alarm
activation sends the local clock first, then the alarm 300 ms later.

#### Notifications

See [Responses](#responses). State and fragment caches belong to the current
connection; reconnecting makes the public values unknown until reported again.

#### Services

`adjustable_bed.set_alarm` configures one bed-local alarm with Sunday-first
weekday bits. P2 retains its raw alarm type. P3/P5 normalize the one-shot repeat
byte while keeping the enabled flag derived from the original inputs. P4 keeps
that byte and BCD-encodes calendar fields. Headboards and P1 offer no bed alarm.
`adjustable_bed.sync_clock` sets the receiver's local clock on P2 through P5.

#### Evidence

The five formats reproduce literally through existing encoders. Hardware
behavior, raw advertisements, GATT properties, long-save interpretation and
radio-loss cleanup need confirmation from users after release.

## Notes

Wi-Fi provisioning, LAN/cloud control, accounts, phone alarms and notifications,
HTTP device information, firmware update and unrelated companion infrastructure
are outside this integration's direct BLE controls.
