# Smart Comfort seats

**Status:** ❓ Needs testing (both app profiles are statically verified; no hardware captures)

**Credit:** Reverse engineering by [kristofferR](https://github.com/kristofferR/ha-adjustable-bed)

## Known Models

Reclining sofas and seats selected by the system-reply codes below. Logical
addresses describe transport targets, not physical left/right. A stored motor
count does not hide controls: both apps bind head, reclining and lumbar in every
recognized layout. Actual installed actuators remain hardware dependent.

Select the exact app in manual setup and supply its Bluetooth MAC. There is no
safe automatic app selector in Home Assistant's parsed advertisement fields.
The apps use absolute raw scan-record offsets with two OR predicates and discard
their allocated service filter. No name rule or strict advertised UUID is proven.

Notification subscription precedes the system query. Failure or the system-query
timeout fails connection setup; a valid unknown model on the first connection
never enables arbitrary seat controls. Unknown codes retain a previously known
mapping, matching the app's parser behavior. HA owns adapter selection, discovery,
link retry, serialized writes and notification CCCD setup.

### Framing and checksum

Framed controls and queries are eight bytes, with complement sum over the first
seven. A full valid frame sums to 255 modulo 256. Motor/memory words are little
endian. Seat masks are exactly `1 << address`: 01, 02 or 04. Motor/basic-accessory
masks occupy byte 5, device-query masks byte 6, and RGB combines its mask with
10 in byte 6. No broadcast or combined-direction builder is proven.

Motor: `E5 FE 16 low high mask 01 checksum`.
Accessory: `E5 FE 16 value argument mask group checksum`.
RGB: `E5 FE 16 blue green red (mask | 10) checksum`.

Rename is raw, without checksum, padding, terminator or framing. The Java app
uses its default charset; only ASCII is portable enough to expose here. Use the
standard `adjustable_bed.rename_device` action.

### Write Mode

The Android apps inherit the runtime characteristic's write type; they do not
select ATT response mode. HA selects response writes when the connected
characteristic advertises `write`, otherwise requires `write-without-response`.
No application PIN, key exchange, characteristic read, MTU or connection-priority
request is established. SYNARGY's recovered notify guard uses OR, not a notify-bit
AND test; platform subscription success still decides whether HA can proceed.
The corresponding SYNERGY predicate is unproven.

### Command encoders

Examples use seat 0, brightness 30 and RGB 18/52/86 (decimal). Brightness accepts
whole numbers 4..100, RGB components 0..255. Reading lights have no color command.
Cup and base screens share the base brightness/RGB builder; only power differs.

### Responses

Every notification is one complete checksum-protected frame; no reassembly or
retry is inferred. Callbacks are bound to the connected peripheral.

| Reply | Fields | Home Assistant behavior |
|---|---|---|
| System, A0 B1 56 | Model byte 3; flags at 4 + logical address | Bit 0 cup, bit 1 base, bit 2 reading; higher bits ignored |
| Device, other A0 B1 opcode | Signed reading brightness at 4, reading on if 5=0, cup on if 7=0; unsigned RGB 8..10; signed base brightness 11, base on if 12=0 | Group-scoped report, no invented seat discriminator; ignored fields 3 and 6 stay ignored |
| Ripple, B0 B1 B2 | Unsigned u32 little-endian at 3, 7 and 11 | Three raw diagnostic counters in frame order; no angle/percentage conversion |

HA rejects empty, truncated, bad-checksum and unmatched payloads. The apps accept
lengths 13 and 15 for device/ripple, overlapping their checksum with a data field.
HA requires at least 14 and 16 respectively so those fields are disjoint. These
are deliberate parser safety bounds, not claimed minimum hardware lengths.

App ripple callbacks reorder counters 1/3/2, while artwork restores frame order.
Baseline subtraction and integer image bins describe illustrations, not calibrated
movement. HA preserves raw unsigned values without applying those graphics.

### STOP and release behavior

Each held movement captures both its logical seat and neutral frame. Release
uses a fresh cancellation event after the profile delay, including on cancellation
or a failed movement write. The complete delay and write are shielded and drained
before cancellation can release serialization. The apps instead read mutable command/seat state in
a delayed callback and retain a motor timer across disconnect. HA never resumes
that retained movement after reconnect. Explicit STOP sends neutral immediately
to the selected logical seat; serialized command cancellation first releases any
running movement to its captured seat. No hardware watchdog interval is known.

## Profiles

### SYNARGY

**App:** [Smart Comfort by SYNARGY](https://play.google.com/store/apps/details?id=com.synargy.okin) 1.1.0 (12), `com.synargy.okin`

**Status:** ❓ Needs testing

#### Setup

Detection: none. Choose Smart Comfort by SYNARGY explicitly. After connecting,
the Logical seat select lists only the model's selectable addresses. A three-seat
layout without a controllable middle never exposes address 1. Seat order and
rotation never become left/right pairing. The selected seat survives BLE reconnects and entry reloads in a process-local
HA session scoped to this address and app profile. Each system reply validates
it against the current model. A cold session starts with address 0 if allowed,
otherwise the first selectable address. This is one peripheral, with no inferred paired-bed topology.

#### Controls

Covers and direction buttons expose all three app-labelled axes. Home is a held
button; it is not an autonomous Flat preset. Standard memory actions send prepare
then the requested recall or save exactly once. Save deliberately does not trigger
the app's possible release-time recall. Prepare's firmware meaning is unverified.

Accessory buttons expose each proved power action. The RGB light and native
brightness control drive the shared base/cup color channel; cup power remains a
separate button. The shared RGB light uses base power when the selected seat
has it, otherwise cup power. Reading brightness has its own number. Capability gates apply
to the selected seat on every write, including entities discovered on another
seat. State reports are labelled group-scoped because the apps copy the same
values to all seats. Requery with the seat select or a reconnect after remote use.

#### Timing

See the generated profile table. Normal button taps use a bounded pulse count;
`hold_control` provides an explicit duration, with refresh and neutral cleanup.
The SYNARGY-only post-discovery notify delay is preserved. Android's scan,
discovery and operation timers are platform behavior, not additional HA sleeps.

#### Notifications

All three response branches above are consumed even with angle sensing disabled.
Raw feedback sensors have no physical unit. No dedicated ripple enable/query is
proven, and no extra request is invented.

#### Services

Use standard movement, `hold_control`, memory, RGB light and rename actions. The
Home button supplies the held control `home`.

#### Evidence

The accepted SYNARGY artifact proves the exact command bytes and model/flag
mapping. Local onboarding uses an app-only password, never BLE authentication.

### SYNERGY

**App:** [Smart Comfort](https://play.google.com/store/apps/details?id=com.synergy.okin) 2.2.0 (16), `com.synergy.okin`

**Status:** ❓ Needs testing

Behaves as the [SYNARGY profile](#synargy) for proved BLE controls, except as below.

#### Setup

Detection: none. Choose Smart Comfort (`com.synergy.okin`) explicitly.

#### Timing

The post-discovery notify delay is unproven, so this profile adds no delay there.
This is an HA policy, not a claim that the SYNERGY app has zero delay. App-specific
listener, background-navigation and motor-runnable guard evidence stays distinct;
HA uses its own serialized lifecycle and cancellation policy.

#### Evidence

The independently accepted SYNERGY artifact reproduces all its frozen commands
with this codec. No one-sided SYNARGY guard, onboarding, persistence or color-step
width claim is imported into it.

## Notes

Physical directions, STOP/watchdog behavior, real GATT properties/security,
notification lengths and seat scope, counter units/limits, model flags, memory
prepare/release and shared accessory semantics need real-user captures after a
beta or release. No maintainer hardware acquisition or immediate testing is needed.
Wi-Fi, cloud/accounts, network administration, OTA and unrelated companion UI are
outside this integration's product boundary.
