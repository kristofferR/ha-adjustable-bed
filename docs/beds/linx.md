Model and transport are independent. The two mixed restored-state choices
also preserve the saved intervention selector independently of generic writes:
JSON intervention follows the generic destination, while binary intervention
always writes directly to UART. The app's running service flag chooses
where unchanged event83/event92 buffers go. JSON commands and alarm-slot clears
therefore retain their JSON bytes on the UART route too. This is verified app
routing; peripheral acceptance of that mixed format remains unverified.

### Framing and checksum

The JSON carrier has no terminator, checksum or encryption. Control commands
use the app's Gson field order; requests use its JSONObject insertion order.
The AA instruction builder uses a finite key switch and a complemented byte sum;
unsupported values produce its zero payload. The two special memory-like words
set an additional high byte. These formulas establish no alarm-choice names.

UART startup sends ASCII text, not decoded hex. Its checksum passes through
Java decimal-string and hexadecimal conversions, then makes a single underflow
correction. An eight-character lowercase suffix can result. The implementation
preserves that behavior rather than normalizing it to one byte.

AB intervention and status frames retain their literal trailer bytes. Those
bytes are not a computed CRC. JSON intervention multiplies hold minutes by 60 with Java integer arithmetic;
UART intervention narrows its stored integer parameters to bytes.

### Responses

Complete A00A indication JSON updates the internal bed-mode cache. Its selector uses
the app's literal substring check, including its match on `bedmd` value 20 and
its whitespace sensitivity. Quest consumes that cache at a new touch; Orbes
retains it for the current connection. The hold captures its selected command
once, so an arriving notification cannot change an active gesture's cleanup.

Quest's `data.apld` reports off or 10/20/30-minute timer indicators (the
**Massage timer** sensor), and `data.mgmd` reports the mode indicator (**Active
massage mode**). These are reported state, not success acknowledgements for
commands. The Android light callbacks are empty, so `blsw` has no proven
meaning and stays in the support bundle's raw notification capture. The bed
mode cache only selects command parameters and is not an entity. No angle or
position is inferred.
HA keeps valid updates fresh within the session instead of copying Android's
15-field UI freeze.

The UART setup consumer accepts exactly eight bytes beginning with `0x8e`.
Byte 4 equal to 2 selects version bytes 5/6. The first pair is parsed as decimal;
the next two uppercase hexadecimal nibbles are dotted components. A nondecimal
first pair is an invalid-version result, not a fabricated firmware version or
an uncaught exception. Byte 4 equal to 1 reports connection failure. Other
lengths, prefixes and selectors are ignored. There is no checksum or ACK match.
The version is the disabled-by-default **Firmware version** diagnostic sensor,
with the reply result as its `linx_setup_reply` attribute. Both are separate
from HA's actual BLE connectivity and setup admission. No HTTP registration is performed.

Self-check consumes `chkStatu`, `headPlus` and `footPlus`. Its completion and
fault fields preserve the app's leading binary-string interpretation; the
ripple fields are diagnostic counts, with session-scoped maxima across checks. Android's randomized current displays
are never exposed as measurements. A self-check times out locally without
claiming hardware failure. Old callbacks and timeouts cannot update a newer
connection.

### STOP and release behavior

Quest movement and Orbes combined movement release with the JSON zero key.
Orbes individual head/foot movement releases with the AA zero instruction on
the same selected BLE route. A standalone STOP uses the combined JSON release.
Tap presets, memory recalls, light, massage, snore intervention and alarm clears
have no extra invented release frame.

Movement cleanup is awaited inside the command lane with a fresh cancel event
and the captured connection and characteristic. A replaced connection cannot
receive an older gesture's cleanup. HA serializes commands and alarm clears;
it does not reproduce Android's callback gate that drops STOP or its shared
alarm array/counter that skips, resumes or overreads slots after unrelated
writes. A failed alarm clear has no latent continuation.

## Profiles

### Quest

**App:** [Linx](https://play.google.com/store/apps/details?id=com.keeson.connectedbed) 1.0.7 (27), `com.keeson.connectedbed`

**Status:** ❓ Needs testing

#### Setup

Choose **Linx**, **Linx 2.5 Q**, the BLE transport and the exact Bluetooth name. A name observed on the live BLE link takes precedence
over the saved name for command identity.
New app sessions default to this model and A00A. UART and the two mixed-state
routes are explicit restored
BLE route, not a Wi-Fi administration setting. Legacy LVrestore/LVrelax select
UART in the app; Quest/Relax/Restore/Rewind select A00A. These old labels do not
supply a separate current control layout. MyBed's status-field presence selects
A00A even when its value is zero; absence selects UART. Updating the model view
does not change the running transport. HA asks these questions directly without
using account data. There is no app PIN, bond handshake or encryption.

The adapter, MTU negotiation, service discovery and reconnect ownership belong
to Home Assistant's Bluetooth stack. The app requests MTU 243 before subscribing;
HA uses the discovered GATT roles and its negotiated transport. The profile's
startup waits, write chunk limit and query order are in the generated tables.
No private platform MTU API or Android reconnect loop is copied.

#### Controls

Use the head, feet or explicit combined cover. The card can hold each movement
until release. Independent concurrent axes and single-address left/right
addressing are not declared. `ctrm` is not treated as a side selector.
M1–M4 are recall only. The head/foot/timer massage actions and standard mode button retain their own commands;
reported mode does not change the mode button's fixed `statsBo=0` command.

#### Timing

See the generated profile table. The app attempts a held refresh at fixed delay,
but its callback gate means this is not a guaranteed wire rate. HA serializes
writes and skips expired refreshes. Finite holds use elapsed monotonic time;
short holds start when the first wire write is admitted. Slow writes never
cause catch-up bursts. A leased hold uses the scheduler's bounded deadline.

#### Notifications

See [Responses](#responses). Cached reports are invalidated on disconnect and
belong to the physical receiver, including in a two-address pair.

#### Services

- `adjustable_bed.hold_control`: the six head/feet/both directions.
- `adjustable_bed.linx_clear_alarm`: clear one slot, or all six when omitted.
  The bed acknowledges no alarm inventory, so no clear state is shown.
- `adjustable_bed.linx_snore_intervention`: stored hold minutes, lift time and
  up-speed parameters, defaulting to the app's values. This is a manual BLE
  effect, not phone recording or snore detection. Its single later status query
  always targets A00A, even after a UART intervention. It runs only while the
  same connection survives, cannot reconnect or keep the link alive, and is
  cancelled on disconnect/unload. The follow-up uses the app's signed integer
  milliseconds calculation, with elapsed time measured from dispatch; slow writes
  do not restart that delay. No cloud-result polling is simulated.
- **Run self-check** starts the bed's self-check; on A00A, **Self-check result**
  shows its outcome with the fault and ripple fields as attributes. UART carries
  no self-check reply, so that route has no result sensor. Status is queried
  on every connection and then arrives by notification, so there is no refresh
  button.

#### Evidence

Unit079's repaired direct BLE scope, including the conditional destinations and
UART reply, is statically verified. The accepted report remains PARTIAL because
the account-fed alarm catalog and corresponding rows are absent. Hardware
qualification is separate external beta/release work, including mixed-format
UART acceptance, Orbes release behavior, startup checksum and diagnostic fields.
No maintainer acquisition or immediate hardware testing is required.

### Orbes

**App:** [Linx](https://play.google.com/store/apps/details?id=com.keeson.connectedbed) 1.0.7 (27), `com.keeson.connectedbed`

**Status:** ❓ Needs testing

#### Setup

Choose **Orbes BR 40+ Slim Q VAVE Linx**. Transport and name remain independent
questions, as described for Quest.

#### Controls

Head, feet, both, Flat, Zero G, Sleep / anti-snore and light. There are no memory
slots or massage entities on this layout. The individual-axis AA release and
the combined JSON release follow [STOP and release behavior](#stop-and-release-behavior).

#### Timing

Uses the same app refresh interval, with its own bed-mode fallback and cache
retention policy in the generated profile table.

#### Notifications

UART exposes the firmware version diagnostic. Quest-only massage indicators
are hidden.

#### Services

The static alarm-clear and manual snore services also target this model. In a
two-address pair, a child device target keeps that physical side's model,
transport, name, callbacks and cleanup. The generic parent does not propagate
one side's app choices to its partner.

#### Evidence

Same accepted unit079 scope and external hardware qualifications as Quest.
