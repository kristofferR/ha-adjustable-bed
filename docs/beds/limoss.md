# Limoss

**Status:** ❓ Needs testing (the app profiles are APK-verified with hardware unverified; the legacy route is unverified)

**Credit:** Reverse engineering by [kristofferR](https://github.com/kristofferR/ha-adjustable-bed)

One wire codec (TEA-encrypted ten-byte `DD` frames on FFE0/FFE1) serves a legacy
route and two audited app profiles. This guide covers the codec first, then one
section per profile. See [Protocol codecs and app profiles](../design/protocol-codecs.md)
for the architecture.

## Known Models

- Limoss adjustable bed controllers
- Stawett-branded controllers using the same protocol
- Limoss bed and chair receivers operated by the Limoss Remote app: bed layouts
  with 2, 4, 6, 8, 10 or 12 keys, chair layouts with 2, 4, 6 or 8 keys
- Chairs and beds operated by the FSM Relax app on Limoss-style FFE0 receivers

A shared FFE0 service or device name cannot identify either app's layout, so both
app profiles are explicit choices.

### Home Assistant setup

The bed-type list has one **Limoss / Stawett: Limoss Remote and FSM Relax apps,
Stawett and older Limoss controls** row, and the **Limoss / Stawett** brand
opens the same question. The receiver's name and service are shared, so setup
asks which app you use:

| Answer | Route |
|---|---|
| Limoss Remote app | [Limoss Remote](#limoss-remote): bed or chair, light, massage, reversals and the optional artwork theme |
| FSM Relax app | [FSM Relax](#fsm-relax): bed or chair, light, massage, reversals and the eight memory names |
| No app: Stawett or older Limoss controls | The [legacy route](#legacy-route) |

Each route keeps its own controls, feedback and memory format; none is
translated into another. For an existing bed, open the entry's three-dot menu
and **Reconfigure** (see
[Changing the app or layout](../CONFIGURATION.md#changing-the-app-or-layout-of-an-existing-bed));
**Keep** leaves the entry as it is. A change to Limoss Remote first checks for
the app's FFE0 service and its notifying FFE1 characteristic. Leaving Limoss
Remote with its light or massage enabled sends the app's OFF commands before
saving, as Configure does; if they fail or are cancelled, the saved setup stays.
A change also drops the old app's own settings. **Configure** keeps routine
settings, including Limoss Remote's light, massage, reversals and theme; the app
changes only through **Reconfigure**.

## Wire codec

`codec/limoss.py` owns the transport, the frame, the cipher, the command bodies and

timing and key tables.

### Framing and checksum

Every command is a five-byte body, `opcode p1 p2 p3 p4`. On the wire it becomes one
ten-byte frame:

| Bytes | Content |
|-------|---------|
| Plaintext | `AA`, the body, the low byte of the sender's counter, then the low byte of the sum of those seven bytes |
| Frame | `DD`, the plaintext encrypted as one TEA block, then the low byte of the sum of the first nine bytes |

- The cipher is 16-round TEA over two big-endian 32-bit words, with the static key
  `55551494 74385555 55551494 74385555` and delta `9E3779B9`. There is no session
  key or nonce; the counter is inside the plaintext.
- Example: FSM Relax STOP `FF 00 00 00 00` at counter 32 is plaintext
  `AA FF 00 00 00 00 20 C9` and frame `DD 1C CD 6B 60 1A 4A F1 01 E7`.
- Who owns the counter differs per profile (see the profile summary). The counter
  byte wraps 255 to 0.

### Responses

Replies use the same frame and carry the request's opcode in the first body byte.
Each profile reassembles them differently:

| Profile | Parser |
|---------|--------|
| Legacy route | The first ten bytes of each notification, validated: header, both checksums and the `AA` marker |
| Limoss Remote | Stream reassembly from each `DD`; any ten bytes are decrypted unchecked, as the app does |
| FSM Relax | Stream reassembly, validated; an invalid frame resynchronizes one byte later |

The stream parsers keep at most one partial frame. Reply contents per profile are
under each profile's Notifications.

### STOP and release behavior

- STOP (`FF`) ends held movement. The app profiles send it with the reversal
  flags; the legacy route sends it clear.
- The recall release (`03`, always clear) ends an FSM Relax memory recall and a
  Limoss Remote calibration.
- Release and STOP frames always use a fresh cancellation event, so a stop or a
  cancelled action still releases. The app profiles shield their release burst
  against repeated cancellation and attempt every frame even after a failed one.
- Counts and spacing are in the generated timing table.

### Vectors

`tests/limoss_vectors.py` freezes each profile's wire frames (body, counter,
frame) and its command bodies. The app profiles take them from their accepted
reports' test vectors; the legacy route takes the frames the pre-v5 controller
built. `tests/test_limoss_vectors.py` proves every frame round-trips through the
codec and both parsers, that each profile sends only its frozen bodies, and that
the Limoss Remote key tables match an independent fixture.

## Profiles

### Legacy route

**Status:** ❓ Needs testing

#### Setup

- Detection: a device name containing `limoss` or `stawett`, with the shared
  FFE0 service as a confidence boost. The bed type is `limoss`. A lowercase
  `limoss` name that FSM Relax also matches is offered as ambiguous.
- Write mode follows the characteristic: with response when it has `write`, else
  without response when it has `write-without-response`.

#### Controls

| Control | Opcode |
|---------|--------|
| Back up / down | Motor 1 |
| Legs up / down | Motor 2 |
| Head up / down | Motor 3 on 3+ motor beds, else motor 1 |
| Feet up / down | Motor 4 on 4-motor beds, else motor 2 |
| Flat | `51` held, then STOP |
| Massage toggle | Vibration zone 1 (`60`) |
| Massage zone 1–6 | `60`–`65`; other zones are rejected without a write |
| Light toggle | `70` |

- The reported motor count takes precedence over the configured one, clamped to
  2–4.
- Memory presets are software-based: save copies the latest raw positions into a
  local slot; recall sends one set-position command per stored motor. Recall is
  offered once a slot is saved. The capability reply sets the slot count.

#### Timing

Movement repeats one frame (one counter value) at the entry's motor pulse count
and delay, then sends STOP; see the generated timing table for the defaults,
which follow the apps' sending interval. Position queries are spaced 30 ms apart.
Recall writes each stored motor once, at the recall interval, with no release.

#### Notifications

- On connect, the route subscribes, sends the capability query and waits up to
  2 s for the reply, then queries the motor positions.
- Capabilities: motor count is the low nibble of the system byte, memory slots the
  low nibble of the fourth byte, and the vibration-zone count the third byte.
- Positions are unsigned 32-bit raw values. HA converts them to estimated angles
  against a per-motor maximum that grows with larger samples and shrinks after
  repeated low samples, reset on reconnect.

#### Evidence

Reverse engineered from `com.limoss.limossremote` and `com.stawett` before their
audits. The legacy route sends only its frozen bodies, which equal the pre-v5
controller's.

### Limoss Remote

**App:** [Limoss Remote](https://play.google.com/store/apps/details?id=com.limoss.limossremote) 7.1.8 (44), `com.limoss.limossremote`

**Status:** ❓ Needs testing (APK-verified, hardware unverified)

#### Setup

- Detection: none. Answer **Limoss Remote app** in the
  [Limoss question](#home-assistant-setup), then choose bed or chair and its
  local lamp and massage controls.
- The source selects the first exact FFE0 service, then its first exact FFE1
  characteristic, which must support notification and a write property. Each
  write binds that selected object, including after reconnect; unsubscribe uses
  the same object and owning client.
- The app inherits Android's write mode without a proven override. HA writes with
  response when `write` is available, else without. This is a host transport
  policy, not a claim about the artifact's inherited mode.
- The sequence is the app's global counter: it advances when a command is
  built, including packets whose later write fails, so every repeat and release
  has a fresh value. Logical batches are built together to preserve cross-receiver
  ordering. The Java signed-int wrap and low-byte behavior are retained.

**Layout selection**

- The receiver supplies key count, system/motor count, configuration and memory
  capacity.
- Recognized system ranges (`10`–`1F` bed, `20`–`2F` chair) select the layout;
  the chosen product supplies the fallback for an unknown system code.
- Unsupported key counts use the source's eight-key fallback. A motor count of
  zero falls back to half the key count.
- Configuration 1 selects the eight-key chair's custom Alpha ordering.
- Every rendered lamp/massage combination is retained, including blank cells and
  omitted combined/shift directions. The key tables are generated above.
- Controls use literal motor channels rather than unproven physical axes or
  angle units.

**Local settings**

- Four reversal flags are independent local settings.
- Lamp and massage selections change the available controls, not measured
  hardware state. Enabling a feature changes the local layout without opening a
  Bluetooth link.
- Disabling a previously selected lamp or massage feature first sends its OFF
  burst, then saves the selection. Switching a standalone entry away from Limoss
  Remote also turns off its selected optional features before saving the new
  profile. Failed OFF writes leave the saved selection unchanged.
- The settings action supports the same transaction. For paired or multi-target
  service calls, every selected OFF burst must finish before any feature
  selections are saved. A failure or cancellation retains the previous local
  selections even if some hardware writes succeeded.
- Replacing a queued or active OFF transaction also keeps its previous selection;
  a normal scheduler return alone does not establish burst completion.
- Fresh capability updates defer entity reloads through every selected service
  phase, including preflight and terminal persistence. BLE links still release
  between sequential sides. Reloads resume only after the transaction and any
  active sibling command have released their command lanes.
- App artwork themes are retained as a local preference in diagnostics; HA keeps
  its own theme and does not copy app artwork.

**Paired beds**

- Two-address pairs retain independent profiles, reversal flags, features and
  memories per child.
- Select each receiver's profile before pairing; unpair first to change those
  profiles or convert the pair to another protocol. Shared paired options do not
  replace child settings.
- This profile has no single-address side selector.

##### Home Assistant setup

Answer **Limoss Remote app** in the [Limoss question](#home-assistant-setup). Choose bed/chair, local lamp and massage controls, four reversal flags and an optional app artwork preference. Live replies select the rendered key layout and memory capacity. These settings belong to each physical receiver, including paired children. Disabling a selected feature sends its ten OFF frames before saving; enabling only changes the local layout. Generic pulse, angle and motor-count settings are hidden for this profile.

#### Controls

- Held controls send the opcode with the reversal flags; the generated held
  table names each channel. Motor channels have up/down/stop covers where both
  directions occur in the selected table; named buttons expose every rendered
  action. A combined-down control is held, not a flat preset.
- A button or cover activation holds its action for **one second**, an HA policy
  separate from the app's refresh cadence.
- All actions on a physical receiver share the global motor resource. STOP
  releases that receiver's active control.
- Light and massage OFF utility buttons send their OFF burst without a motor
  release.
- The app has no named flat, zero-gravity or TV preset, position slider, massage
  intensity feedback, lamp ON/OFF feedback, synchronization, PIN or native bond
  workflow.

**Eight local memories**

- The device-reported capacity limits slots 1–8. These are app-local captured raw
  positions, not firmware preset writes.
- Save buttons and `save_preset` query each reported motor sequentially, then
  atomically persist the complete captured slot for that physical address. The
  supported capture domain is one to four motors. A failure, timeout or
  cancellation preserves the previous complete slot.
- Capacity above eight or a motor count above four is rejected before any save
  or recall command, avoiding source array crashes and an unparsed fifth-motor
  query.
- Recall buttons and `goto_preset` hold a stored memory for one second; give
  `goto_preset` a `duration` to choose another hold.
- Recall requires a stored motor-1 row. Sparse rows for the other reported motors
  are allowed and sent in motor order. Raw signed 32-bit values are preserved bit
  for bit without inventing distance or angle units.
- Memory names and positions, and the reported versions and serial, survive
  controller recreation, entry reload, unpair/re-pair and integration restart as
  the physical target's app state, until no entry owns the bed.
- The reported capabilities stay in the config entry because they decide the
  entities.
- Changing the selected protocol preserves the stored app memory data; other
  protocols do not use it. No source-backed clear-memory action exists.

#### Timing

Hold, stop, recall, calibration and feature-off counts and intervals are in the
generated timing table.

- The tick is also the minimum spacing between write starts: HA serializes ATT
  calls and waits for each to complete. Each ATT call has a two-second host
  deadline; this is not an artifact timing claim.
- Ordinary controls ending before the first tick send no command and no release.
- A memory recall resends its batch of set-position frames at the recall interval
  for the whole hold, then releases. Its frames share the same write lane.
- A requested duration limits refreshes; cleanup happens outside that deadline.
  The first command error remains the reported error.
- A renewable hold (`hold_owner` and `hold_generation`) refreshes at the same
  tick until its lease runs out, then sends the STOP burst. STOP ends it at once.

**Information transaction**

- After subscribing, HA sends the capability query, retrying it every second,
  then the hardware and software queries in reply order. The host bounds this to
  ten seconds, including lane, pacing and write waits.
- A fresh capability reply is required even when capabilities are cached.
  Restored values populate offline diagnostic sensors but do not establish a live
  session.
- The app opens controls on that reply, so missing version replies may use up the
  remaining budget without blocking startup. A write failure or timeout,
  cancellation or disconnect still fails the transaction.
- An explicit information refresh stays strict and reports incomplete metadata.
  Completed fields survive later failures and reconstruction.
- Changed capability snapshots refresh the offline layout and request an entity
  reload after the link and paired command lanes are released.
- There are no Device Information Service reads or idle position queries.

#### Notifications

| Reply | Parameters | Exposed as |
|-------|------------|------------|
| `00` / `01` | Four bytes | Hardware / software version string |
| `02` | Key count, system, vibration, configuration (high nibble) + memory count (low nibble) | Capability diagnostics |
| `05` | | Calibration **reply received** |
| `06` | Signed big-endian 32-bit | Serial |
| `10` / `20` / `30` / `40` | Signed big-endian 32-bit | Raw motor 1–4 position |

- Version strings use the source's signed-byte concatenation.
- Position sensors are explicitly **raw**, have no physical unit, and create no
  angle sliders or estimated positions. An unsolicited `06` keeps its signed
  serial; there is no serial query.
- The receive buffer belongs to one physical receiver, is cleared on reconnect,
  and never combines bytes from different receivers.
- A save query accepts matching replies only after its write reaches ATT. Earlier
  and idle replies can update raw diagnostics but cannot contribute to a memory or
  issue queries.
- There is no native request ID: a delayed same-opcode reply arriving after a
  query is indistinguishable from its reply.
- Replies never establish authentication, measured lamp or massage state, or
  physical motion completion.
- Diagnostics expose raw capability fields, chosen product, exact layout, visible
  opcodes, reversal flags, theme preference, local memories and the app sequence.

#### Services

- `adjustable_bed.hold_control` accepts one currently rendered control and a
  duration from 0.1 to 60 seconds, with millisecond precision. The control names
  are the generated Limoss Remote channels.

  ```yaml
  action: adjustable_bed.hold_control
  data:
    device_id: YOUR_DEVICE_ID
    control: motor_1_up
    duration: 0.5
  ```

- With `hold_owner` and `hold_generation` the hold renews: each call within the
  lease extends it, and the STOP burst follows when renewals stop. See
  [Renewable holds](../SERVICES.md#renewable-holds).

- `limoss_remote_calibrate` requires `confirmed: true`, a duration, and a
  memory-capable receiver. It holds calibration and always attempts its release
  burst once a command has been built. A calibration reply is reported as
  **reply received**, not proof of completion.
- `limoss_remote_features` accepts both `underbed_light` and `massage` booleans.
- `limoss_remote_rename_memory` accepts `preset` and `name`. Names are local and
  may be empty; renaming keeps the positions and updates button labels without
  reconnecting.
- Before held movement, calibration or memory execution, services refresh
  receiver startup and validate every selected target before moving any. A
  connection is ready only after that session's fresh capability reply;
  concurrent callers share one startup. Sequential pairs release each validation
  link before opening the next. Cached capacities allow offline editing but never
  admit a new movement session, and each execution rechecks its live layout.
- Target a paired child device, or supply `side: left`, `right` or `both`.

### FSM Relax

**App:** [FSM Relax](https://play.google.com/store/apps/details?id=com.limoss.fsmrelax) 1.9 (20), `com.limoss.fsmrelax`

**Status:** ❓ Needs testing (APK-verified, hardware unverified)

#### Setup

- Detection: none on its own. Answer **FSM Relax app** in the
  [Limoss question](#home-assistant-setup). The exact case-sensitive lowercase `limoss` name adds FSM Relax as an
  ambiguous candidate to the Limoss detection, so the choice stays explicit; the
  focused chooser also applies when that candidate advertises FFE0.
- The source also checks complete raw scan-record text at an index greater than
  zero and rejects null names; HA does not expose that complete Android record,
  so it is never reconstructed from unrelated advertisement fields.
- After profile selection, setup uses normal connection verification when
  available; it requests no OS bond or pairing step.
- The connection must expose exactly one FFE0/FFE1 role. Every write is without
  response even when the characteristic advertises only generic write; the source
  does not inspect those property bits, so HA reports actual transport failures
  instead of inventing a profile rejection. Subscription uses Bleak, without
  guessed descriptor UUIDs, GATT reads, MTU or priority changes.
- The counter is kept per bed across controller replacement and reconnect; a cold
  HA process starts at zero. Devices have separate counters and memory locks.
- Choose the chair or bed layout explicitly (chair is the app default). The bed
  layout has separate optional light and massage settings. Four reversal flags
  become four unchanged `00`/`01` bytes in held controls, STOP and calibration.
- Vibration count, versions and serial never select a layout or enable a
  feature. Layout labels describe the app's icons; physical wiring is unverified.

| Capability byte | Meaning |
|-----------------|---------|
| Key count | 2/4/6/8 keys; any other byte falls back to 8 |
| Vibration count | Reported only; selects nothing |
| Memory count | Unsigned big-endian 16-bit; HA exposes up to eight device-local slots |

Half the key count selects 1–4 raw memory motors. Valid capabilities enable
controls immediately; optional version queries cannot revoke them on timeout.

##### Home Assistant setup

Choose the **Limoss / Stawett** row and answer **FSM Relax app** in the
[Limoss question](#home-assistant-setup); FSM Relax is not a row of its own.
Then choose the chair/bed layout, optional light/massage controls and four
reversal flags on its own step. These settings are local app
configuration, not inferred hardware identity. Options include eight local memory
names, with blank names resetting M1–M8. Raw memory values have no known units.
This profile section covers exact controls, quarantine and calibration.

#### Controls

- The key count and options select the generated FSM Relax key table, in order,
  including asymmetric tables where light replaces a combined direction.
- Each action appears as `command_XX` (for example `command_12`) and as a native
  button labelled as in the generated held table. The chair layout labels
  `12`/`13` Footrest up/down and `22`/`23` Chair back up/down.
- Labels are the app's intended meaning, not verified hardware semantics. Light
  and massage controls are held actions with no invented boolean or measured
  state. No firmware Flat preset, physical-axis slider, six-zone massage toggle,
  RGB, brightness or timer is inferred.

**Local memories**

- Save Memory 1–8 reads each reported raw motor in index order, sending the next
  query immediately after the expected reply, then atomically stores the complete
  set in a physical-address-specific HA record. Slots map to local groups 0–7; the
  slot number is never sent over BLE. An unsolicited reply never saves a slot.
- Signed 32-bit values have no known physical units, scaling, angle or
  percentage.
- Memory buttons and `goto_preset` send each stored target once, in motor order.
  Motor zero must exist; absent later rows are skipped. The default button hold
  is the motor pulse count times the tick; this is a local HA gesture policy, not
  an app-proven preset duration or arrival deadline. Give `goto_preset` a
  `duration` to choose another hold.
- A normal release follows any remaining queued targets. Cancellation skips unsent
  targets and still attempts the whole recall release.
- `goto_preset` validates every target's stored motor-zero row, signed raw values
  and quarantine before any bed moves. Valid stored targets validate offline;
  execution still needs a fresh live capability subscription.

**Reply correlation and quarantine**

- There is no echoed request ID or counter correlation. Expected-opcode and
  connection guards do **not** guarantee a reply is fresh.
- After a timeout, cancellation or uncertain memory write, HA keeps the prior
  slots and quarantines memory operations until the connection is replaced and a
  fresh subscription and capability reply arrive. Resubscribing on the same
  connection does not clear quarantine.
- A device-retained reply after reconnect, or a delayed byte-identical reply
  during a new same-opcode request, may still be indistinguishable.

**Names and persistence**

- Options expose exactly eight local memory names. A blank field resets that slot
  to M1–M8. Editing names never writes BLE.
- Names are entry options and the capability snapshot is entry data; raw targets
  and the serial are app state for the physical bed. All survive restart and
  controller replacement; removing the last entry that owns the bed removes its
  app state.
- Within one entry and address, live and cached offline controllers share the
  current slots, names, capabilities and serial, so recall preflight never sees a
  stale snapshot. Different addresses and entry owners keep separate models;
  ownership transfers load the retained store, and final removal clears its
  cached models and stored record.
- Identical capability snapshots and serial observations skip storage writes. A
  memory save persists atomically; a failed write keeps the previous value.

#### Timing

Held controls, STOP and the recall release use the tick in the generated timing
table, from one monotonic origin. A recall writes each stored motor once at the
recall interval, holds for the rest of the gesture, then releases.
A renewable hold refreshes at that tick until its lease runs out, then sends
the STOP burst.

- The capability query retries every 1000 ms within a four-second HA setup window.
- The optional hardware and software queries start 120 ms after the preceding
  reply, taking the command lock only for each write.
- Each position-save query gets one attempt and a one-second HA wait. That timeout
  is a safety bound, not an artifact deadline.
- Writes are serialized; late writes are still attempted, so nominal offsets are
  not a promise of physical timing.

#### Notifications

| Reply | Exposed as |
|-------|------------|
| `00` / `01` | Hardware / software version string |
| `02` | Capabilities (key count, vibration count, reported memory count) |
| `04` | Acknowledgement observed, not correlated to physical arrival |
| `05` | Calibration observed |
| `06` | Signed serial |
| `10` / `20` / `30` / `40` | Raw signed motor values |

- Raw motor and serial fields are signed big-endian 32-bit.
- Version strings keep signed-byte concatenation: a nonnegative first byte, the
  signed second byte, a dot, then optional nonnegative third and fourth bytes.
  `01 80 02 ff` becomes `1-128.2`.
- A notification over 1024 bytes clears the buffer. Unknown opcodes are ignored.
- A link drop fails pending queries with a connection error so setup can use the
  coordinator's remaining retries; explicit cancellation still propagates.
- An offline controller without a capability snapshot has incomplete entity
  discovery. A loaded entry's first stored capability reply requests a deferred
  reload after link release, including the parent of a pair, so actions and
  memories appear without a manual reload; initial setup needs no reload.
- Old connection callbacks cannot overwrite the current session. Entry-owned
  background query tasks stop on teardown.
