# JMC400

**Status:** ✅ Tested with the Jensen app profile on a JMC400 (motion, position reports, massage and memory recall); its lights, fan and device memory, and the Svane Remote profile, await user confirmation

**Credit:** Reverse engineering by [kristofferR](https://github.com/kristofferR/ha-adjustable-bed)

## Known Models

- Jensen JMC400 (JMC 400) control boxes, including the LinON Entry box
- JMC400 beds driven by the Svane Remote app

### Framing and checksum

A frame is an opcode, then its payload: six bytes, or five for the config
request and the PIN. There is no length, checksum or sequence number.

| Opcode | Frame |
|--------|-------|
| `0A` | Config request |
| `10` | Motion, presets, the position query and go-to |
| `12` | Massage |
| `13` | Light |
| `14` | Fan |
| `1E` | PIN |

### Command encoders

`10 code 00 00 00 00` carries motion and presets. A motion code combines one
head bit (`01` up, `02` down) and one foot bit (`10` up, `20` down), so `10 11`
raises both and `10 21` raises the head while lowering the foot; `00` is STOP.

- `position(head, foot)` and `head_foot(position)` read the four position bytes
  as head and foot, unsigned 16-bit little-endian, the byte order of a JMC400
  capture ([#631](https://github.com/kristofferR/ha-adjustable-bed/issues/631)).
  Both apps keep the bytes opaque.
- The light and fan frames end in bytes each app chooses; see
  [Choosing a profile](#choosing-a-profile).

### Responses

The box answers on the command characteristic. `position_report()` decodes the
position report; the Jensen controller reads the config and PIN replies itself.

| Report | Layout | Jensen Adjustable Sleep | Svane Remote |
|--------|--------|-------------------------|--------------|
| Position | `10 state` + four position bytes | State and head and foot positions | Bytes 2-5 opaque; byte 1 ignored |
| Config | `0A` + config bytes | Features and box type | Not read |
| PIN | `1E status` | Status `1` unlocks | Not sent |

A position report has at least six bytes. `state` is the active motion code:
`00` idle, `FF` in reply to a query.

### STOP and release behavior

- STOP is `10 00 00 00 00 00`. Held motion ends with it, sent even when the
  command was cancelled.
- The box moves on its own after a flat, memory recall or go-to frame; STOP
  interrupts the move.
- Each profile's Timing describes when it sends STOP.

### Vectors

- `tests/jmc_vectors.py` freezes each profile's frames and the reports the
  tests feed back.
- `tests/test_jmc_vectors.py` proves that each round-trips through the codec,
  that every fixed frame a profile sends is frozen, and that every JMC400 write
  in the wire snapshot is one of its profile's frozen frames.

## Profiles

### Jensen Adjustable Sleep

**App:** Adjustable Sleep 2.0.37 (106) and 2.0.29 (98), `air.no.jensen.adjustablesleep`

**Status:** ✅ Tested on JMC400 (motion, position reports, massage and memory recall, [#146](https://github.com/kristofferR/ha-adjustable-bed/issues/146) and [#631](https://github.com/kristofferR/ha-adjustable-bed/issues/631)); lights, fan and device memory await user confirmation

The `jensen` bed type. The [Jensen guide](jensen.md) covers setup, the PIN
option, features, memory and movement feedback.

#### Setup

- **Detection:** service UUID `00001234`, or a device name containing `JMC400`
  (the app's rule); the integration also accepts names starting with `jmc`.
- **Write mode:** the app writes without response; the integration uses a
  response only when the characteristic offers writes with response alone.

The app's session start:

1. Subscribe to notifications on `1111`.
2. PIN frame `1E` + the four digits, each digit as a byte (`1E 03 00 06 00` for 3060).
3. Config request `0A 00 00 00 00`.

The integration additionally sends `10 FF 00 00 00 00` and waits for its
position reply. The app does not send it, but the bed answers it, and some beds
ignore the first flat after reconnect until they see a `0x10` frame
([#217](https://github.com/kristofferR/ha-adjustable-bed/issues/217)). The iOS
app sends STOP at the same point for the same effect.

#### Controls

| Control | Frame |
|---------|-------|
| Head or foot up and down | The motion frame for that section |
| Back and legs together | One motion frame with both sections, through `adjustable_bed.linak_move_simultaneously` |
| Stop | STOP |
| Flat | `10 81 00 00 00 00` |
| Save and recall device memory (box type 4) | `10 40 00 00 00 00`, `10 80 00 00 00 00` |
| Recall a stored memory, or a position slider | Go to position, with the stored or computed head and foot positions |
| Massage | `12 head foot wave H M` (levels 0-10, 0 = off) |
| Light | `13 02 level 00 H M` (level 1-10; every light kind uses output `02`) |
| Light off | `13 02 00 00 00 32` (a fixed frame in 2.0.37) |
| Fan | `14 level 00 H M 50` (level 0-10) |

`H M` is a timer. The Android app encodes it incorrectly (hexadecimal digits
parsed as decimal) and the iOS app ends up sending `00 00`. The #631 iOS capture
shows massage running with `00 00`, so the integration always sends `00 00` and
offers no timers.

#### Timing

- The app repeats a held frame every 300 ms and sends STOP once on release. A
  [renewable hold](../SERVICES.md#renewable-holds) (`timed_move`) refreshes at
  300 ms; a finite press uses the entry's pulse settings, then STOP.
- Flat is sent once by the app; the integration sends a short burst of at least
  two, which keeps flat reliable on beds that drop the first frame.
- Flat, memory recall and go-to are followed until the bed stops; see
  [Movement feedback](jensen.md#movement-feedback).

#### Notifications

Position reports are pushed while the bed moves and in reply to `0x10` frames.
The app treats the four position bytes as opaque and echoes them in go-to
frames, so both use the same byte order.

The app shows no position scale. The integration's percentage mapping uses
anchors measured on one JMC400
([#631](https://github.com/kristofferR/ha-adjustable-bed/issues/631)):

| Axis | Flat | Fully raised |
|------|------|--------------|
| Head | 30000 | 30804 |
| Foot | 30000 | 29369 (the value falls as the foot rises) |

Other units may differ slightly; values beyond the anchors clamp to 0 or 100 %.

The config report answers `0A 00 00 00 00`, for example `0A 05 03 08 01 75`.
The app reads bytes 2 and 4 by treating their decimal digits as hexadecimal (a
byte of 16 means `0x16`); the integration does the same.

| Byte 2 bit | Feature |
|------------|---------|
| `0x01` | Head massage |
| `0x02` | Foot massage |
| `0x04` | Light |
| `0x10` | Fan |
| `0x40` | Under-bed light |

Byte 4 is the box type. Box type 4 has device memory; box type 2 also offers the
app's scripted comfort mode (see the ledger).

The PIN reply's byte 1 is read as hex text; only `1` means unlocked. A
rejection is logged as a warning.

#### Evidence

- The clean-room APK Protocol Audits of Adjustable Sleep 2.0.29 (98) and 2.0.37
  (106): the profile sends only its frozen frames.
- The JMC400 support bundle and capture in
  [#631](https://github.com/kristofferR/ha-adjustable-bed/issues/631): the
  position byte order, the anchors, and the go-to and massage frames.

### Svane Remote

**App:** [Svane Remote](https://play.google.com/store/apps/details?id=com.svane.svaneremote) Version 1.8 (8), `com.svane.svaneremote`

**Status:** ⚠️ Artifact-verified; physical hardware unverified

The `svane` bed type's `svane_remote_jmc` variant, shown as **Svane Remote app
(JMC400)**. The [Svane Remote guide](svane.md) covers both of the app's
routes; this section lists the JMC400 frames.

#### Setup

- **Detection:** none. Choose the JMC400 bed in the
  [app and bed question](jensen.md#home-assistant-setup); a scanned name
  containing case-sensitive `JMC` suggests it, following the app's own rule.
- **Write mode:** without response when the characteristic offers it,
  otherwise with response; a characteristic that offers neither is refused.
- Initialization subscribes to `1234/1111` on both routes. The software query
  it then sends goes to the app's own `f92a/a592` role and is not a JMC400 frame.

#### Controls

| Control | Frame |
|---------|-------|
| Head and feet held, alone or together | The motion frame with every held axis |
| Release and global STOP | STOP |
| Svane position (`preset_zero_g` button) | `10 81 00 00 00 00` |
| Memory recall (Read, TV) | Go to position with the slot's stored bytes: `10 04 81 38 81 13` and `10 04 82 73 82 04` before a save |
| Lamp on or level | `13 02 level 01 00 64`, the level's low byte as a Java int |
| Lamp off | `13 02 00 00 00 00` |

The default multi-service route writes the same lamp frames to its own lamp
roles.

#### Timing

Held axes run in 100 ms passes; see the Svane guide's
[Command Timing](svane.md#command-timing) and [Release](svane.md#release).

#### Notifications

The old-role record must have at least six bytes and start with `10`. Bytes 2-5
are kept as the opaque position a memory save stores; byte 1 is ignored.

#### Evidence

- APK Protocol Audit row130 of Svane Remote Version 1.8 (8): the JMC400 route
  sends only its frozen frames.
